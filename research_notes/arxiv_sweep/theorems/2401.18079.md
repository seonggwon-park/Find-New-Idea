## Q1. Pre-RoPE gain: exact numbers and the explanation

**Number.** Appendix H, Table 10 (per-channel Key, per-token Value, uniform int3, LLaMA-7B, Wikitext-2):

| Datatype | Scheme | PPL | KV (GB, 128K) |
|---|---|---|---|
| fp16 | – | 5.68 | 64.0 |
| int3 | post-RoPE | 7.05 | 12.0 |
| int3 | pre-RoPE | 6.23 | 12.0 |

Quote (Appendix H): "As shown in Table 10, pre-RoPE Key quantization achieves higher accuracy than post-RoPE quantization, with an improvement of 0.82 perplexity for 3-bit quantization with the LLaMA-7B model. These results show that the rotary positional embeddings make Key quantization more challenging due to mixing pairs of channels with different magnitudes. Pre-RoPE quantization thereby allows for more accurate quantization at low precision."

Sec. 3.2 restates: "The benefits of pre-RoPE Key quantization are highlighted in Appendix H, yielding 0.82 perplexity improvement on Wikitext-2 for 3-bit LLaMA-7B quantization."

So: 0.82 PPL is **one model (LLaMA-7B), one bit-width (uniform int3, no NUQ, no outliers, no sink handling), per-channel keys with offline-calibrated ungrouped scales**. The paper gives no pre/post-RoPE ablation for any other model, bit-width or with nuq/outliers. The Figure 1 chain is: int3 per-token 10.87 → per-channel 7.05 → pre-RoPE 6.23 → nuq3 5.94 → +1% outliers 5.75 (fp16 5.68).

**Explanation given (verbal, not derived).** Sec. 3.2: "The challenge with caching Key vectors after applying this rotation is that it leads to mixing pairs of channels by different amounts for different positions in the sequence, as shown in Appendix C (since it jointly rotates pairs of channels by different angles depending on the position in the sequence). The post-RoPE activation distribution is also shown in Figure 2, demonstrating how the rotation between pairs of channels leads to less consistent channel magnitudes. This makes it harder to quantize Key activation channels which would typically have consistent large-magnitude values."
Figure 2 caption: "(i) Keys pre-RoPE exhibit clear outliers in specific channels across different tokens; (ii) after applying RoPE, the distribution becomes less structured and there are less consistent magnitudes for outlier channels (this is expected, as RoPE applies a rotation operation between pairs of channels)".
Appendix C gives only Eq. (2), the rotation matrix with θ_i = 10000^{-2(i-1)/d}, and the element-wise (rotate-half) formulation used by the fused kernel. No MSE bound, no frequency-band analysis.

**Crucial counter-result the report does not mention — the sign of the pre-RoPE gain flips under per-token Key quantization.** Appendix P, Table 20 (LLaMA-7B, uniform, Keys quantized **per-token**, Wikitext-2):

| Datatype | PPL pre-RoPE | PPL post-RoPE |
|---|---|---|
| fp16 | 5.68 | 5.68 |
| int4 | 6.02 | 5.98 |
| int4-gs128 | 5.76 | 5.77 |
| int3 | 14.68 | 10.87 |
| int3-gs128 | 6.28 | 6.17 |

Quote (Appendix P): "These results show that post-RoPE Key quantization is superior to pre-RoPE Key quantization when quantizing Keys per-token. This is because when rotating an outlier channel with large average magnitude and another channel with smaller average magnitude together, at some positions in the sequence, part of the magnitude from the outlier channel will be shifted to the smaller channel. This partially mitigates the impact of the outlier channel on skewing the quantization range for some of the tokens in the sequence. As such, for our baseline comparisons, we use post-RoPE per-token Key quantization to serve as a stronger baseline."
Consequently all baselines in Tables 1/18/19 are post-RoPE per-token, and KVQuant rows are pre-RoPE per-channel (Table 1 caption).

## Q2. Rationale for per-channel Keys vs per-token Values

**Number.** Appendix G, Table 9 (LLaMA-7B, uniform int3, Wikitext-2; PT = per-token, PC = per-channel):

| Datatype | Key dim | Value dim | PPL |
|---|---|---|---|
| fp16 | – | – | 5.68 |
| int3 | PT | PT | 10.87 |
| int3 | PC | PC | 223 |
| int3 | PC | PT | 7.05 |

Sec. 3.1: "By leveraging per-channel quantization for Keys and per-token quantization for Values, we observe a 3.82 perplexity improvement on Wikitext-2 for 3-bit LLaMA-7B quantization." (10.87 − 7.05 = 3.82.) Per-channel Values are catastrophic (223 PPL).

**Rationale for per-channel Keys (distributional, Sec. 3.1):** "We observe that the Key matrices tend to have distinct outlier channels, which have larger average magnitudes than other channels ... due to the differing average magnitudes between channels, the values within a channel are easier to quantize when grouped together than the values across different channels. ... By sharing the scaling factor and zero-point along the channel dimension, this will naturally group together values with similar magnitudes, thereby mitigating the impacts of outlier channels on other channels when quantizing to low precision." Also: "The Value matrices exhibit both outlier channels as well as outlier tokens (although these outliers are less extreme than the outlier Key channels)."

**Rationale for per-token Values (an explicit hypothesis, Appendix G):** "we observe that per-channel quantization for Values actually performs worse than per-token quantization. We hypothesize that this behavior is because per-channel Value quantization leads to greater error accumulation in particular output values (since the result of the attention scores multiplied by one channel of the Values will be localized to a single value in the output vector), which leads to greater quantization error at later model layers. Another concurrent work, KIVI [26], observes similar behavior for per-channel Value quantization, which they attribute to the fact that per-token Value quantization confines the error to each token. Assuming that the output is a weighted sum of only a few important tokens (as only a few attention scores are large), a perturbation in these tokens can lead to significant degradation. Per-token Value quantization therefore ensures that the quantization of unimportant tokens does not adversely impact the important tokens."

Both justifications are magnitude/outlier-structure arguments plus an error-localization hypothesis. **No optimality proof, no softmax-bias argument, no mention of noise heteroscedasticity.** Practical reason also given (Sec. 3.6): per-channel scales cannot be updated online as tokens arrive, so Keys are calibrated offline; per-token Value scales/outlier thresholds are computed online (top-k offloaded to CPU, Table 15).

## Q3. Which outliers are isolated; attention-sink handling

**Outliers (Sec. 3.4, Appendix J).** Dense-and-sparse: a fixed fraction (0.1% or 1%) of numerical outliers per vector is kept in fp16 in a CSR/CSC sparse matrix; the rest is normalised to [−1,1] and quantised with the nuqX datatype. The threshold is **per-vector**: "a separate threshold per-channel for per-channel quantization, or a separate threshold per-token for per-token quantization), rather than a single outlier threshold for each layer." Key thresholds are calibrated offline (and excluded from scale calibration), Value thresholds computed online per token. Table 12 (LLaMA-7B, nuq3, pre-RoPE PC keys / PT values):

| Datatype | % outliers | Outlier dim | PPL | KV (GB) |
|---|---|---|---|---|
| fp16 | – | – | 5.68 | 64.0 |
| nuq3 | – | – | 5.94 | 12.0 |
| nuq3 | 0.1% | per-matrix | 5.89 | 12.2 |
| nuq3 | 0.1% | per-vector | 5.82 | 12.2 |
| nuq3 | 1% | per-matrix | 5.85 | 13.3 |
| nuq3 | 1% | per-vector | 5.75 | 13.3 |

Sec. 3.4: "by removing 1% of numerical outliers using per-vector outlier thresholds, we achieve an additional 0.19 perplexity improvement on Wikitext-2 for 3-bit LLaMA-7B quantization, which is within 0.07 perplexity of the fp16 baseline."
Table 14 (Appendix L): with 1% outliers, offline-calibrated Key scales match online scales exactly (5.75 vs 5.75); without outliers offline costs 0.03 (5.94 vs 5.91).

**Attention-sink handling (Sec. 3.5, Appendix K).** Only the first token is kept in fp16; it is also excluded from calibration. Quote: "we demonstrate that due to the Attention Sink phenomenon, the model is disproportionately sensitive to quantization error in the first token. By keeping only the first token in fp16, we can attain perplexity benefits, particularly for 2-bit quantization. A similar observation has also been made in another concurrent work [23]. Note that when retaining the first token in fp16, we account for this during the calibration process as well, meaning that we ignore the first token when deriving the nuqX datatype and when calibrating the scaling factors and zero points offline for the Keys." Table 13 (Wikitext-2; X = without, O = with sink-aware):

Appendix K: "For all bit widths (4, 3, and 2-bit) and in both dense-only and dense-and-sparse quantization settings, Attention Sink-Aware quantization consistently yields perplexity improvement. Notably, the perplexity gain is more pronounced at lower bit widths and without sparsity. We observe particularly significant improvements for Llama-3 models, with perplexity improvements of 0.25 and 0.13 PPL for nuq2-1% on Llama-3-8B and Llama-3-70B, respectively."
Note: the paper does not separate whether the first-token sensitivity comes from its Key or its Value, and this sensitivity appears under **per-channel** Key quantization (there is no per-token-Key sink ablation). Sink-aware is on for every KVQuant row in Tables 1/18/19.

## Headline claims (Table 1 / Sec. 4.1, Wikitext-2, with sink-aware)
- LLaMA-7B: KVQuant-3bit 5.87, KVQuant-3bit-1% 5.75 (fp16 5.68); KVQuant-2bit 7.23, -2bit-1% 6.01; KVQuant-4bit-1% 5.69. Baselines int3 10.87, nf3 7.33, ATOM-3bit 6.17, FlexGen-3bit 5.93.
- Table 18: Llama-3-8B 3bit-1% 5.64 vs fp16 5.54 (= 0.10, so "under 0.1" is borderline); 2bit-1% 6.04 (= 0.50). Mistral-7B 3bit-1% 4.82 vs 4.76. Llama-3-70B 3bit-1% 2.63 vs 2.59.
- Claimed: 4.8× KV compression at 3 bit, 1M context LLaMA-7B on one A100-80GB, 10M on 8 GPUs, up to ~1.7× kernel speedup vs fp16 matvec (abstract).

## Paper's own limitations / future work (Appendix S, verbatim)
"While our work enables accurate long-context length inference by reducing the memory requirements, there is significant work required for training long context length models with greater than 100K context length. This work is orthogonal to our efforts, which are constrained to efficient inference with long context length models. Additionally, our latency benchmarking results currently focus on memory-bandwidth bound generation rather than prompt processing (where we need to compress multiple Keys and Values at once). Finally, in the current end-to-end implementation, there are inefficiencies in how memory allocation is handled for updating the sparse matrix (where the data corresponding to the previous tokens have to be copied when concatenating them with the data from the new token). In future work, we plan to optimize this by doing blocked allocation to avoid overheads from reallocating memory."
(Nothing in the limitations about the pre-RoPE gain being quantizer-dependent, about group size, or about other positional encodings.)
