# 2607.26515 — HiFloat4 Format for End-To-End RL Post-Training of LLMs (Rollout-ResQ)

- Exists: yes. Mak et al. (Huawei, 13 authors), v1 2026-07-29, cs.LG, no comment/journal_ref -> preprint.
- Source text: scratchpad/papers/2607.26515/2607.26515.txt (line numbers below). Quoted text is untrusted data.
- Already confirmed in verify/batch_13.md: Table 1 numbers, TIS=5.0 in all runs, FP4 is simulated, no entropy/KL reported. Not repeated except where needed.

## What kind of evidence
- **No theorem, lemma or proposition anywhere.** All claims are empirical. The only analysis is a FLOP count (Sec 5.4).
- Single run per configuration as far as the text shows (no seed, std or CI reported). 3B runs are ~200 GRPO steps (Fig 5a/b), 7B runs ~140 steps (Fig 5c).
- Evaluation precision of the final policy is not stated. Table 2 = Mean@1 (greedy); Table 3 = Mean@32 (l.799-800).

## Claim 1: rollout activation quantization dominates
- Text (l.587-592): "by isolating the components of the rollout phase, we identify activation quantization as the primary bottleneck. While weight-only quantization (W4A16) in the rollout (Row 3) maintains a competitive accuracy of 85.22% for HiF4 and 81.57% for MXFP4, activation-only quantization (W16A4, Row 5) leads to a sharper decline to 84.30% for HiF4 and 77.71% for MXFP4."
- Critical reading: for HiF4 the A4-vs-W4 gap is 0.92 pp (85.22 vs 84.30), single run, one task (Qwen2.5-3B, GSM8K). Only MXFP4 shows a clear gap (3.86 pp). Also full FP4 rollout (82.03 / 73.31) is worse than W16A4 (84.30 / 77.71), so weight quantization contributes roughly as much again; "dominant" is a fair reading for MXFP4 and a thin one for HiF4.
- Mechanism (Sec 4.2, l.640-650; Fig 1-2): post-quantization activation sparsity rises sharply; "In specific layers, such as the down projection of transformer block 1 and 2, sparsity exceeds 80%, indicating a 'zero collapse'"; fraction of blocks containing outliers "strongly correlates" with zero collapse (Fig 2, correlation not quantified).

## Claim 2: higher-precision trainer + FP4 rollout is worse
- Abstract (l.36-38) and contributions (l.138-141): "Restoring only the training policy to higher precision performs worse than uniform FP4 training, indicating that the rollout–training mismatch, not training-side noise, is the principal failure mode."
- Table 1 (Qwen2.5-3B, GSM8K, GRPO; HiF4 / MXFP4): FP4/FP4 82.03 / 73.31; BF16-train/FP4-rollout 78.01 / 50.57 (l.580-584 "catastrophic drop ... significantly worse than even the fully quantized settings").
- Caveats: (i) what is worse is the *final trained policy's GSM8K accuracy*, not "the rollouts" themselves; (ii) one model/task, single run, not repeated for 7B (Table 3); (iii) TIS threshold 5.0 is on in every run (App. A l.1490), so this is "mismatch persists despite token-level TIS", which strengthens rather than weakens the claim, but the paper never measures KL(rollout||train) or IS-ratio statistics to show mismatch is the cause — "mismatch" is an inference from accuracy only.

## Claim 3: 4.9% -> 1.1% (and 13.6% -> 5.3%)
- Abstract l.42-46 attributes it to "Qwen2.5-3B and Qwen2.5-Math-7B". **The numbers come only from Table 2, Qwen2.5-3B, GSM8K-test, Mean@1, and are absolute percentage points, not relative %:**
  - HiF4: naive 82.03 (−4.93) -> Rollout-ResQ-S2:4 85.90 (−1.06), BF16 86.96.
  - MXFP4: naive 73.31 (−13.65) -> S2:4 81.65 (−5.31).
  - l.809-820: "Naively applying HiF4 and MXFP4 ... degrades performance by 4.93% and 13.65% on GSM8K-test ... Rollout-ResQ-S2:4 reduces these gaps to 1.06% and 5.31% on GSM8K-test".
- Same table, Math500 (3B): HiF4 naive 44.6 (−16.6) -> S2:4 52.6 (−8.6), best variant S50%^{32x64} 55.8 (−5.4); MXFP4 naive 27.8 (−33.4) -> S2:4 46.4 (−14.8), Dense 48.2 (−13.0). OCC baseline: HiF4 GSM8K −2.73, Math500 −9.4.
- Table 3 (Qwen2.5-Math-7B, DAPO-Math-17K, Mean@32, HiF4 only — no MXFP4 7B run): BF16 27.29/12.08/64.53/74.59 (AIME24/AIME25/AMC23/Math500). Naive HiF4 −11.14/−4.79/−9.37/−15.19; S2:4 −6.56/−3.54/−8.75/−5.64; Dense −12.81/−3.12/−8.91/−5.57. On 7B the residual gap is 3.5–8.8 pp, far from "1.1%".
- Oddities: MXFP4 Dense and S2:4 have identical GSM8K (81.65); on 7B AIME24 Dense (−12.81) is worse than naive HiF4 (−11.14) while S2:4 (−6.56) is much better — sparsifying the correction beating the dense correction by 6 pp suggests run-to-run noise is large relative to the effects.

## Method (Sec 4.3, Eqs. 3–5)
- ΔX = X − Q(X) (3); dense: Ŷ = Q(X)Q(W)^T + Q(ΔX)Q(W)^T (4); Rollout-ResQ: Ŷ = Q(X)Q(W)^T + S(Q(ΔX))Q(W)^T (5). S ∈ {top-50% channels by L2, 2:4 magnitude, top-50% 32x64 blocks}. Tensor-level residual (unlike block-level in ref [64]). Applied only in rollout; training forward/backward are plain FP4.
- Overhead (Sec 5.4, l.1134-1145): assumes FP4 = 4x FP16 throughput; Dense = mdn (2x vs FP16), S2:4 = 3/4 mdn (2.67x). Not counted: computing ΔX, quantizing it twice, top-2-of-4 selection, and the fact that hardware 2:4 sparse tensor cores sparsify a structured operand at fixed layout (activation-side 2:4 needs per-call metadata generation). No measured kernel.

## Paper's own limitations (Sec 6, l.1150-1158, close quote)
"Due to the lack of native FP4 hardware support, all experiments rely on FP4 simulations where simulation overhead dominates training time, preventing direct measurement of real speedup and efficiency gains. Additionally, the prolonged runtime has prevented us from extending experiments to extremely large models or datasets ... this work focuses exclusively on 50% sparsity across all sparsity patterns ... exploring varying sparsity levels to better characterize the accuracy-efficiency trade-off remains an open direction."
